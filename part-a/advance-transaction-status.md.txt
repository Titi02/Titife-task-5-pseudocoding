# Part A1 — Pseudocode for `advanceTransactionStatus`

## Function header

**FUNCTION:** `advanceTransactionStatus`

**INPUTS:**
- `providerReference` (string): Identifies the payment transaction.
- `userId` (string): Identifies the user associated with the transaction.
- `amount` (number): The transaction amount in kobo.
- `currency` (string, optional): The payment currency.
- `planType` (PlanType or null, optional): The subscription plan.
- `interval` (BillingInterval or null, optional): The billing interval.
- `paystackTransactionId` (string or null, optional): The payment provider's transaction ID.
- `status` (TransactionStatus): The requested transaction status.

**OUTPUT:** A transaction record containing the resulting transaction details.

**SIDE EFFECTS:**
- Reads a transaction record from the database.
- May create a transaction record.
- May update an existing transaction record.

**FAILS WHEN:**
- A database lookup fails.
- Creating a transaction record fails.
- Updating a transaction record fails.

## Numbered pseudocode steps

1. CALL the database to find the earliest transaction matching the supplied provider reference.
2. IF no matching transaction exists, CALL `upsertTransaction` with the supplied parameters and immediately RETURN its result.
3. IF a matching transaction exists, check whether its current status is `INITIATED` or `VERIFIED`.
4. WRITE the supplied amount to the existing transaction.
5. WRITE the supplied currency, or `ngn` if the currency is `undefined` or `null`.
6. IF the existing status is `INITIATED` or `VERIFIED`, WRITE the requested status. OTHERWISE, preserve the existing status.
7. IF `planType` is not `undefined`, WRITE its supplied value, including `null` if that is the supplied value.
8. IF `interval` is not `undefined`, WRITE its supplied value, including `null` if that is the supplied value.
9. IF `paystackTransactionId` is not `undefined`, WRITE its supplied value, including `null` if that is the supplied value.
10. CALL the database to update the existing transaction with the specified changes.
11. RETURN the updated transaction record.

## Important observation

An existing transaction with status `SUCCESS`, `FAILED`, or `REFUNDED` keeps its current status. Other fields may still be updated.

## Code inspection findings

I inspected the actual `advanceTransactionStatus` implementation in `src/server/payments/transaction.ts`.

The code confirms three main branches:

1. **No existing transaction:** The function calls `upsertTransaction` and returns its result. The helper may create a transaction with the requested status.
2. **Existing status is `INITIATED` or `VERIFIED`:** The function updates the status to the requested status.
3. **Existing status is `SUCCESS`, `FAILED`, or `REFUNDED`:** The function preserves the existing status while allowing other supplied fields to be updated.

**Additional edge case:** `advanceTransactionStatus` selects the oldest matching transaction. However, `upsertTransaction` uses an unordered lookup. If duplicate records share a provider reference, the two functions may select different records.
